# Grok Bot via independently scoped Cursor authorization

Grok Bot is an independent provider/card, separate from Cursor monthly model pools and SuperGrok. It uses Cursor authentication because that is the vendor-supported account entry. The add/reauthorize flow reuses the necessary Cursor nonce/PKCE code and account-owned ephemeral WebKit view; it does not read the Cursor editor, Safari, `.grok/auth.json`, Grok Bot sand-secrets or any existing credential.

CursorAccountAuthenticator/Session/View accept a provider argument defaulting to `.cursor`, limited to `.cursor` and `.grokBot`. Provider, local UUID, remote subject and actual JWT are part of the fingerprint; a Cursor envelope cannot query Grok Bot or vice versa. Existing Cursor credential fingerprints remain compatible (the original seed was already the cursor raw value). Each Grok Bot service account has its own nonce, saved credential, cache and reminder identity, even when the same remote Cursor account signs in twice.

Login is the pinned non-OAuth protocol: `https://cursor.com/loginDeepControl` with nonce, base64url verifier SHA-256 challenge, mode=login, redirectTarget=sand and team-selection support. Poll `https://api2.cursor.sh/auth/poll?uuid=...&verifier=...`;404 means pending, denied/expiry/rate-limit/network/cancel remain distinct. JWT sub/exp is read only to build the exact WorkosCursorSessionToken cookie and enforce account/expiry matching; backend auth validates the token. No unsupported refresh exchange is invented, and the returned refresh token is not stored. Login query validation uses the selected provider, cancellation/close prevents credentials being published by a stale attempt.

Both devices directly `POST https://cursor.com/api/dashboard/get-sand-usage-status` with `{}`, restricted Cookie, JSON headers and mandatory `Origin: https://cursor.com`. This REST-cookie route is chosen over historical Connect RPC or the unrelated SuperGrok billing routes. Automatic Cookie/cache reuse disabled; redirects refused. Common secure local/iCloud account lifecycle supplies restore, multi-account, reauthorize/delete and Watch independent querying after credential arrival.

TokenPulse does not add those advertised allowances, guess the selected backing pool or treat them as a monetary balance; it displays only this service's response.

An individual meter requires affirmative hasNonZeroIncludedLimit, no explicit zero/pooling exclusion, and an actual finite nonnegative usagePercent (percent scale0…100). Numeric1 is not Bool; absent percentage is not implicit0. An explicit no-personal-allowance or pooled-org response is successful categorical quotaStatusText with empty windows, clearing prior quota and schedules. Unknown/contradictory flags remain unreadable, included-but-missing percentage is noQuotaWindows; marketing upgrade text is not presented as current plan or remaining balance.

`grokBot.weekly` is one independent weekly window. Only a returned valid nextResetTimestampUtc produces a date. currentPeriodStart+7days, next Monday and calendar assumptions are never used. With no date no expected reminder is scheduled; the usual thresholds still apply to valid measurements. Known absent/shared-personal state does not trigger zero/full rings or alarms and the account can still be saved after successful validation. No low-wallet/manual-reset controls. Demo data uses its own isolated weekly snapshot.
