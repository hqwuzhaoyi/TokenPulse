# Claude 网页会话来源身份修复

Pi01反馈的旧Claude网页登录凭证只有cookieFormat／organizationID，没有localAccountID或sourceCredentialFingerprint。旧getter直接取metadata fingerprint而返回nil，导致monitor替换、latest-credential和云端scope守卫对Claude不起作用。已用Pi提供的旧生产代码harness重现错误本地UUID仍可查询、snapshot无来源、getter为nil。

新登录选择组织时由ClaudeWebSession构造webSessionFormat=v1凭证，绑定真实的本机服务账号UUID、固定https://claude.ai origin、会话Cookie和组织，并用WebProviderSession从实际字段重算fingerprint。直接client强制provider=claude、kind=session、expiry、本地UUID绑定；Cookie只允许已核实的sessionKey／sessionKeyV3，组织只允许安全单一路径段。请求禁止自动Cookie，不转发tracking或任意Cookie，snapshot携带和getter一致的来源身份。

旧restrictedHeader凭证继续支持，不全量注销：从实际受限Cookie值（规范化名字顺序）+organizationID+固定origin计算稳定非nil identity，忽略可伪造的旧metadata fingerprint。旧格式没有localUUID时不能凭空恢复绑定，只能保持其真实session/org scope；若旧格式已有显式owner则仍校验。有效旧session仍可正常刷新，仍保留旧Keychain编码，不在一次请求中偷偷转成带新UUID的v1。这样首次刷新前／后及latest credential的identity一致，不会被新的snapshot guard拦住。

显式重新登录属于新的UUID绑定身份，monitor已有换绑流程会清旧scope缓存；新组织／会话刷新失败不能再显示旧组织读数，也不能并回旧scope更晚的同步snapshot。先前完全无身份的缓存无法证明属于当前session/org，第一次绑定时按现有规则清理；这不删除或注销旧凭证。不同格式之间不主张指纹相等，避免把未知旧owner与新owner偷合并。

7个ClaudeSessionScopeTests覆盖新UUID绑定、组织与token分离、旧identity稳定／伪造metadata不生效／不发明UUID、Cookie顺序等价、直接client的provider/kind/owner/expiry/cookie/path拒绝、旧首次refresh不会被fingerprint迁移挡住、失败换绑清旧cache与旧同步拒绝、请求及snapshot来源。root统一执行XCTest。纯Foundation+CryptoKit小模块逐字提取当前producer/client/getter/通用policy，实际运行通过：错误新UUID零请求、旧session仍正常查询且返回稳定来源、不同org/token不同identity、坏Cookie和组织路径拒绝。Swift parser、PBX lint、diff检查通过。

没有读取真实凭证，没有Xcode／模拟器或重复大模块编译。WK视图与reset流程未改；Claude图标和既有接入门槛仍done，不重新开票。真实服务兼容性边界仍按已有接入文档记录。
